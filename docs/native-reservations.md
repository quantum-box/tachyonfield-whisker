# ネイティブ予約業務

PR #38 の基本管理画面から、予約を受け付け、変更し、支払い・取消・引き継ぎまで進める操作を追加した。
比較元は `quantum-box/tachyonfield` の `27b3a5296f735b6811bcb9d49b4de615c07ac9e7`。
ネイティブ側の基準は #38 を取り込んだ `e0fc53176b078e59c194efc9f54efffa8b3ae48c`。

## 対応した業務

| 業務 | アプリの操作 |
| --- | --- |
| 予約を探す | 日本時間の日付選択・前日/翌日・全期間、氏名/予約番号/連絡先のサーバー検索、予約状態・支払状態・種別・設備・担当で絞り込み |
| 予約を作る | 種別・プラン・設備を選び、その日の空き枠から開始日時を入力。登録済み顧客の連絡先反映、人数、総額、前払条件、担当者、備考を確認して登録。保存した予約の詳細を開く |
| 予約を変更する | 日時、設備、担当者、顧客との紐付け、連絡先、プラン、備考、社内メモ追記。請求後の変更禁止と既存値は保持 |
| 状態を進める | 確定・利用完了・来店なし。Webと同様のスタッフ操作として扱い、支払状態をクライアントから変更しない |
| 取消・返金 | 規定と支払済額から取消料・返金額を表示し、理由と明示額を確認して取消。取消履歴を閲覧し、返金待ちは選択した取消イベントの返金を再実行 |
| 支払いを再開する | 請求書付き、または支払リンクだけを作成/再取得。iOSでリンクを開く・コピー・共有。未割当入金は確認対象とメモを指定して記録 |
| キャンセル待ち | 希望日時、順番、元の枠の空きを確認。元の希望または代替日時・設備・料金で繰り上げ、作成した予約を開く。辞退・期限終了も記録 |
| 引き継ぎ | 予約/キャンセル待ちのそれぞれにメモを追加、引き継ぎ済みを記録、理由を付けて撤回。本文を上書きせず、撤回済みも履歴に残す |
| 予約枠を管理する | 設備別の実枠確認、曜日の営業時間・適用期間・季節条件、休業日・臨時営業、生成試算と確定。設定変更後は再生成して実枠を確認 |
| 種別・設備・プラン・予算 | 種別の数量表示/上限・電話受付、設備、料金プラン、日別予算を管理。旧プラン設定・商品連携・未編集属性を保持し、古い画面からの上書きを検知 |
| 通知 | お客様向け3テンプレートを管理し、予約詳細で宛先・差し込み後の件名/本文を確認して送信。社内向けは種別ごとのメール・スタッフ・Slackと通知イベントを管理 |
| CSV | 全期間の予約CSVを明示的に取得し、iOSのファイル保存/共有画面へ渡す。検索/状態の絞り込みが適用された出力とは表示しない |

予約枠、営業時間、休業日、生成、プラン、通知設定の画面は、予約画面内の「予約枠・プラン・通知の設定」から開ける。

## 日時・在庫・料金

日付別一覧の範囲は日本時間の当日0時から翌日0時未満。入力の初期値も `+09:00` に変換し、元の秒を保持する。営業時間の設定と枠生成は、指定したIANAタイムゾーンに従い、日付変更や夏時間の23/25時間の日を扱う。

予約枠の在庫単位は**組数**。一つの予約が開始時刻に対応する一つの枠を1組分使う。人数・利用数を空き組数と比較しない。終了日時はサービス所要時間であり、長時間のプランに対して途中のすべての枠を消費する契約ではない。枠を選んだ後も、保存時の競合はサーバーが判定する。

キャンセル待ちの `availableSlotGroups` が未設定なら「予約枠が未開放」、0なら「満枠」、正なら空き組数を表示する。未開放と満枠を同一に扱わない。

プラン料金は予約全体の料金。人数を掛けない。新規作成でプランを選ぶと、総額・前払い方法・前払額・終了日時を初期化する。スタッフはAPIが許す範囲で作成時の料金や終了日時を調整できる。既存予約のプラン変更では、直接の金額変更を送らない。

金額は整数の最小通貨単位で扱い、前払割合も整数計算で丸める。既存の外貨予約の取消・返金では、表示用の小数とAPIの最小単位を正確に変換する。

## 保存・失敗・競合

- 予約作成は本文の `idempotencyKey`、取消は `Idempotency-Key` ヘッダーを、同じフォームの再送で保持する。結果が不明なまま内容を変えて同じ操作を送らない。
- 書き込み前の再確認で拒否された場合は、まだ送信していないため入力を訂正できる。送信後のエラーは別に扱う。
- 取消は、履歴を保存した後の決済事業者/設定エラーでHTTP 400になることもある。この場合も未実行とはみなさず、「対象と履歴を読み直して確認」から現在の状態と返金再実行へ進む。
- キャンセル待ちの繰り上げは、予約作成と待ち列の更新が一つの原子的な処理ではない。失敗後に繰り上げ先が取得できても、失敗した操作の作成結果との同一性を証明できないため、成功へ昇格しない。予約一覧と待ち列を再確認し、無条件にPOSTを再送しない。
- 待ち列の終了処理では、返されたID・終了状態を要求と照合する。競合で別の人が先に繰り上げた状態を、取り下げ成功と表示しない。
- 取消履歴、入金、通知テンプレートなどの補足情報が取得できない場合は警告を表示し、関連操作を止める。未取得を「履歴なし」とは表示しない。
- 予約枠生成は、対象期間・設定・休業日・試算結果を再確認してから実行する。プレビュー後の変更を検出したら再試算する。
- 休業日・臨時営業は `expectedRevision` を送信する。バージョンのない設定更新は最新値と比較するが、比較と保存の間の競合を完全に排除するものではない。
- テナント・選択レコード・検索条件・画面の生存期間を照合し、古い非同期応答を新しい画面へ反映しない。

## 維持するAPIの境界

予約作成後の人数、任意の料金、前払額、通貨を直接更新するAPIは確認できていないため、編集できるようにはしていない。予約APIの返金は取消と取消イベントに対する再試行であり、新しい任意額の単独返金を実装したとは扱わない。

待ち列のお客様へ空き候補を送り、承諾待ちを管理する専用契約もない。今回の対応はスタッフがお客様と合意した枠で繰り上げる操作。

予約種別の決済・取消ポリシーはWebでも閲覧項目のため、推測で編集APIへ追加しない。プランの対象設備・曜日など、Webのプラン画面で編集されない既存属性も保持する。

CSVの取得は読み取り操作。ネイティブのファイル保存・共有と支払リンク操作はiOSの部品として実装した。リンクを開く/共有することを支払完了とは扱わない。

## 検証

実テナントの予約作成、メール/Slack送信、請求、決済、返金は実行していない。次をfixtureとネイティブ描画ツリーで確認する。

- フォーム初期化→入力→型付きpayloadの往復。氏名・関連ID・数量・金額・日時・未編集属性の保持。
- 実際のInput/tap callbackによる日付選択、空き枠フォーム、通知プレビュー、補足情報の未取得表示、繰り上げ先への遷移、RecordReferenceの名称表示。
- 送信前の拒否、送信後の不確実な失敗、取消の部分成功、同一再送キー、変更したpayloadの拒否。
- JST日界、IANAタイムゾーン、夏時間、取消期限、プランの所要時間・前払割合、旧設定、競合、上限到達。

プロジェクト全体の `cargo test --locked` と、GitHub ActionsのiOS Simulatorビルドを実施する。実行結果はPRへ記録する。ビルドの成功は、実機での業務API往復や共有シートの操作確認済みという意味ではない。
