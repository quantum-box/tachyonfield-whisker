# 予約枠・営業日・予約設定のネイティブ対応

Web 管理画面と API の `27b3a5296f735b6811bcb9d49b4de615c07ac9e7` を基準に、予約枠の運用と設定を追加・補強した。予約本体、決済、キャンセル待ち、顧客への通知テンプレートは別モジュールで扱う。

## 対応した操作

| 画面 | ネイティブでできること |
| --- | --- |
| 空き枠・予約枠 | 場所・設備、複数日、タイムゾーンで検索。空きがある枠だけ・無効な枠を含む条件指定。開始・終了、受付組数、予約済み、仮押さえ、空き組数を確認 |
| 営業時間・予約枠の設定 | 曜日、開始・終了時刻、受付組数、開始枠の間隔を追加・編集・削除。適用開始日・終了日、毎年の営業期間も編集 |
| 休業日・臨時営業 | 休業日を登録。特定日の営業時間を複数指定。設定を編集、または解除して通常の曜日ルールに戻す |
| 予約枠の生成プレビュー | 対象の場所・期間を指定して、新規・更新・無効化・変更なしの件数を確認。その確認済みの条件で実行し、実際の処理件数を表示 |
| 予約種別・場所設備 | 既存の作成・編集・利用停止・削除に加え、編集・削除直前に最新情報を確認。使用中の削除や数量制約はサーバーの判定を維持 |
| 予約の社内通知 | 種別ごとに通知の有効・無効、新規予約・日時場所変更・取消のタイミング、メール・スタッフ・Slackの通知先を編集 |
| 予約プラン | カタログ／旧拡張設定の両保存先の CRUD を維持。旧形式の前払い設定を現在の形式へ正規化し、保存時も方針・割合を保持 |
| 日別予算 | コース・日付・金額・キャディ付き比率の登録・編集・削除。新規登録は有効なコースを使用し、登録済み予算を未確認のまま上書きしない |

## 営業時間と予約枠の区別

営業時間の保存だけでは、公開ページが参照する予約枠は変わらない。操作案内は「営業時間または休業日を保存 → 生成プレビュー → 件数を確認して実行」の順にしている。

`capacity` は同じ開始時刻で受け付ける**予約の組数**。1 組あたりの人数・数量の上限とは別で、`slotIntervalMinutes` もプランの利用時間とは別の設定として表示する。曜日は API に合わせ月曜日 `0` ～ 日曜日 `6`。営業時刻は現地時間の `HH:MM` または `HH:MM:SS` を受け取り、秒を含む形式にして送信する。

週次営業時間は全体置換なので、既存の行の識別情報を画面には出さず保持する。削除した行は意図した変更として送る。適用期間と毎年の営業期間を落とさず、フォームで扱わない `solarWindow` は省略して既存設定を保持する。`rollingWindowDays` も読み取り表示し、保存リクエストから省略する。

## 日付とタイムゾーン

枠一覧の `from` は開始時刻の下限を含み、`to` は上限を含まない RFC 3339 の日時。ネイティブの検索では終了日を含む日付範囲を入力し、その翌暦日の現地 0 時を UTC の上限へ変換する。IANA タイムゾーンデータを使い、夏時間の 23 時間・25 時間の日も扱う。存在しない日時や二通りに解釈できる日時は推測しない。

生成と営業日の特例は、各ルールのタイムゾーンにおける日付をそのまま送る。対象は 1 ～ 366 日。検索用の UTC 日時と、生成用の現地日付を混同しない。

## 変更の競合と保存結果

- 生成プレビューには、場所・開始日・終了日・件数と、その時点の営業時間・営業日の特例を保持する。実行時に日付を別の入力へ差し替えない。
- 実行前に設定を再取得し、再プレビューの件数も照合する。再プレビュー中の変更も再取得で確認する。設定または予定件数が変わったら再確認を求める。
- 休業日・臨時営業は作成時に `expectedRevision` を省略し、既存設定の編集・削除には読み取った版を送る。削除ではクエリ文字列に版を指定する。休業では `windows` 自体を送らず、臨時営業では重複しない時間帯を 1 件以上送る。
- 営業時間、種別、場所、通知、予算は保存・削除前の再取得で変更を検出する。これらの API にはクライアント用の厳密な条件付き更新がないため、再取得と書き込みの間の同時更新まで保証するものではない。
- 予約済み・仮押さえ済みの枠への矛盾は、最終的にサーバーがロック下で判定する。409 などの拒否を成功扱いにせず表示する。
- 生成の成功表示は実行 API の件数を使う。プレビューの件数をそのまま実行結果として表示しない。

## 社内通知の保存

予約種別を選び、設定の読み込みが成功してから編集する。メールは最大 10 件、スタッフは 20 人、Slack は 5 件。宛先の前後の空白と重複を整理し、有効化には 1 件以上の宛先を必要とする。

Slack 接続は取得した候補の名称で選ぶ。未選択は会社の既定の接続。チャンネルは `#front-desk` などの名称で入力できる。接続候補を読み込めなくても既存の設定を消さず、追加・変更した接続は保存直前に再確認する。スタッフも追加した対象だけ現在の名簿と照合する。すでに削除されたスタッフや接続を保存済みの通知先が参照していても、通知の停止や他の宛先の編集を妨げない。

`staffAccountEmails` はサーバーがログインアカウントから解決する項目として扱い、クライアントで作った対応表を送らない。Slack の候補や既存の内部識別情報は、ユーザーの入力項目や読み取り画面に露出させない。

## 料金と予算

料金・予算は整数の円で扱い、浮動小数点を経由させない。キャディ比率と前払い割合だけは 0 ～ 1、小数 4 桁までの入力として検証する。予算の成功応答では、比率の `0` と API が返す `0.0` を同じ値として扱いつつ、金額は整数のまま一致を確認する。

旧プランの `paymentRequirement` や `deposit` / `partial` / `full` / `full_prepayment` を解釈し、現在の `prepaymentPolicy` と前払い割合に引き継ぐ。正規の項目がある場合はそれを優先し、保存時に旧項目を残して古い方針が復活することを防ぐ。他のプラン、未知の属性、拡張設定、利用可能設備の `null` と空配列の違いは従来どおり保持する。

識別情報がない旧設定のプランは、Web と同じ配列位置由来の `plan_1`、`plan_2` などで読み取る。旧設定の保存・削除では設定全体と版を再照合し、読み込み後の並び替え・削除・他の設定変更を検出したら中止する。書き込み時には欠けていた識別情報を各プランへ確定してから対象の 1 件だけを編集・削除するため、削除で残りのプランの識別情報がずれない。生成される識別情報と既存の識別情報が重複する不整合は、別のプランを選び直して処理せずエラーとして扱う。

## 対象外の高度な設定

この追加は通常の営業日・枠生成・社内通知・予約料金・日別予算の運用を対象とする。日出・日没のポリシーや自動生成期間の変更、枠の物理削除、プラン画像のアップロード・AI生成は追加していない。既存の該当設定をフォーム保存で消すことはない。個々の枠を直接書き換える操作の代わりに、検証済みの営業時間／特例と生成 API を使用する。

## 検証

純粋な契約テストで、夏時間と複数日検索、存在しない日時、営業時間の識別情報・季節・適用期間の往復、休業と臨時営業の本文・版、生成対象の固定と変更検知を確認する。社内通知では候補取得失敗時の宛先維持、追加したスタッフ・Slack接続の確認、内部識別情報の非表示、不正な宛先と宛先なしの有効化を検証する。料金の旧形式移行、整数精度を維持した予算変更、未確認の上書き拒否と保存結果の照合もテスト対象。

主な契約根拠は同 SHA の Web `features/reservation-schedule`、`reservation-resources`、`reservation-types`、`reservation-plans`、`daily-budgets`、サーバーの `reservation_api/{schedule_management,schedule_override,slot_generation,type_management,resource_management,staff_notification,product_management}.rs`、`reservation_golf_daily_budget_api.rs`、`packages/staff_notify/src/lib.rs`。

実際のテナントの予約・設定・決済への書き込みは、開発・検証では行っていない。
