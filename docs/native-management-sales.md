# 営業・顧客・予約・人事のネイティブ対応

## 対象と検証元

この変更は `src/management/sales.rs`、`sales_workflows.rs`、`workforce.rs`、`jobcan.rs` に、ネイティブ画面の入力項目とAPI操作を定義する。Web画面の埋め込みは使用しない。

契約の確認元は `quantum-box/tachyonfield` のコミット `73e645adebe3b21dddb83b6d4556ce58b6bee08f`。WebクライアントのAPI定義、フォーム検証、操作ページ、および必要なサーバー側リクエスト定義を照合した。この文書と公開コードには、非公開Web実装の原文を転載していない。

以下は今回実装した操作の範囲。メニューを開けることだけをもって、Webの全操作に対応したとは扱わない。

## データを保持するための実装上の判断

### 金額・日時・参照先

金額を浮動小数へ変換して往復させない。通貨の最小単位を使う契約では共通Money入力、文字列の整数・小数を要求する契約では対応する文字列入力を使う。円固定の予算やキャンセル料は整数で処理する。店舗受取のNanoDollarも、サーバーの整数値を保ったまま表示する。

日時入力には日本時間を明示し、送信時には時差付きの形式に変換する。取引先、顧客、スタッフ、会員プラン、商品マスタ、コースなどはAPIから取得した候補を選ぶ。内部IDを手入力するフォームは作らない。

### 見積・受注・販売契約

見積は `POST /v1/erp/quotations` と `PATCH /v1/erp/quotations/{id}` の正式な明細契約を使う。新規作成は円建て下書きとし、有効期限を空欄にした場合はサーバーの30日後の既定値を利用する。編集中の既存見積では通貨を変えず、Money入力の最小単位を引き継ぐ。税額は値引後の金額を税率ごとに合算してから切り捨て、整数のまま算出する。数量・値引上限・税率・64bitの金額上限を検証する。

Web帳票の発行元・宛先・旧明細情報は、備考に含まれる保存用データを表示前に解読する。フォームには通常の備考・住所・担当者・明細を出し、保存時に元の帳票ひな形と未知の帳票情報を維持して再構成する。明細の追加・削除に合わせて保存用の明細情報も更新する。解読できない情報がある場合は保存を止める。表示用変換で元レコードを変更しないため、競合確認の対象は読み込んだ実際のデータのままになる。

受注の新規作成では未確定状態・手動の作成元を固定する。確定、出荷、完了は順方向の状態操作だけを提示する。出荷時の在庫出庫は受注APIのトランザクションが担当する。出庫または請求済みの取消を提示せず、サーバー側の出庫履歴確認も維持する。既存受注の明細を変更するPATCH契約はないため、取消した手動受注を元に新しい受注を作る操作を明示した。既存の受注ID・状態・請求情報を新しい受注へ送らず、元の履歴を残す。割引済み明細を割引なしで複製することは認めない。

販売契約の有効化・解約は、読み込んだ商業条件・明細・条項・ひな形・作成元を保持し、状態だけを変えた正式なPUTリクエストを送る。内部の版や固定本文を更新引数として捏造しない。専用の有効化手続きを持つ`provider_managed`にはこれらの操作を出さない。ひな形の変更・再適用と削除は下書きに限定し、有効化後に下書きへ戻す操作は提供しない。

保存前には詳細を再取得する。見積・受注は更新時刻と明細などの主要項目、契約は`aggregateRevision`と商業条件・固定本文を比較し、画面を開いている間の変更を検出したら中止する。これらのREST更新APIにはクライアントの期待版を指定する引数がないため、再取得と書き込みの間を原子的に保証するものではない。サーバーが持つ状態遷移・ロック・権限判定に従う。見積作成・手動受注作成・契約作成に未対応の冪等キーを付けて安全な再試行と見なすことはせず、送信結果が不明な場合は共通フォームで再送を止め、一覧で確認する。

### 予約プランの二つの保存先

`GET /v1/erp/reservation-products?includeDisabled=true` の `seeded` を確認する。移行済みの会社はカタログAPI、未移行の会社は `golf_course` 拡張の予約プラン設定を使用する。

更新・削除の前にも保存先と対象プランを再取得し、画面を開いた時から保存先または対象プランが変わっていれば中止する。旧設定の場合は最新の設定全体を基に対象の1件だけを変更し、他のプラン、タイムゾーンなど未知の設定を保持する。カタログでは所有する拡張、予約方式、利用可能リソースの `null` と空配列の違い、未知の属性を保持する。子テーブルの予約枠を属性へ戻すことはしない。

商品マスタに紐付いたプランの名前・内容は商品マスタから取得する。既存の紐付けは変更しない。

旧設定APIには期待バージョンを渡す契約がない。再取得後から書き込みまでの同時更新を、クライアントだけで原子的に防ぐものではない。移行との競合はAPI側でも拒否される。

### 利用受付

新規受付の `requestKey` を画面単位で保持する。利用者の基本情報と受付の同時登録では `newCustomer` を使い、既存利用者の受付では `customerId` を使う。両方を同時には送らない。

対象者・対象物は選択した利用者の会員情報から取得し、アーカイブ済みの対象を除く。対象一覧は固定行で、隠した元の識別子を保持し、選択した行のIDだけを送信する。別の利用者のIDや重複IDを受け入れない。

### ジョブカン取込

ファイルの選択時に内容をメモリーへ取り込み、プレビューと確定で同じバイト列を使う。設定版・出力日時・対象期間・取り込み方もプレビュー時点の内容を保持する。確定時には、プレビューが返した `fileSha256` を付けて送信する。

プレビューには新規・更新・保留・未対応・取消候補・除外行・合計不一致を表示する。阻害要因がある場合は確定できない。表示内容を確認したチェックが入った場合にだけ確定を許可する。入力やファイルを変更すると確認結果を破棄する。送信結果が不明な時に、画面からそのまま重複送信はしない。

取込取消は、選択した取込について勤務日への影響を先に表示する。確定直前に影響を再取得し、内容が変わった場合は再確認を求める。APIに期待バージョンの契約がないため、再確認と確定の間を原子的に固定するものではない。

## 検証

実データの作成・更新・メール送信・SMS送信は行っていない。API契約とローカルfixtureで検証した。

- `sales.rs` の契約テスト: 顧客の編集可否、スタッフの権限、楽観ロック、明細と金額、予約取消の冪等キー、フォームから実リクエストへの変換など。
- `sales_workflows.rs` の12テスト: 保存用帳票情報を含む初期化から編集・送信への往復、未知情報・ひな形保持、旧明細の補完、税率別端数処理・安全整数域を超える金額・外貨、見積の状態制限、受注の正規遷移・出庫/請求ガード・取消後の訂正作成、契約の条件保持と大きな版番号、専用契約の除外。sales全体29テストが独立ハーネスで通過。
- `workforce.rs` の14テスト: 金額の精度、日別予算の識別情報、シフトの不変項目と日付範囲、店舗受取の状態制限、予約プランの未知属性・所有者・他設定保持、保存先変更の検知、利用受付の対象ID、初回登録、SMS同意、ジョブカン設定のコード保持、月次の複数打刻。
- `jobcan.rs` の3テスト: プレビューのSHA・設定版保持、阻害要因と確認チェック、対象期間の整合、取消候補と合計不一致の表示。
- 共通モデルを使ったフォーム初期化→編集→`request_body` の往復で検証。独立ハーネスではworkforceの14テストが通過。プロジェクト全体のネイティブUI・契約テストでもJobcanの3テストが通過した。

主な契約参照は、Webの `features/tenant-sales-classifications`、`store-pickup`、`usage-receptions`、`membership`、`reservation-plans`、`daily-budgets`、`staff`、`staff-attendance`、`cancellation-fees` 以下のAPI・schema・page。予約カタログとジョブカンのサーバー側リクエスト定義も照合した。

追加した見積・受注・契約操作は、同じ参照コミットの`features/quotations`、`orders`、`sales-contracts`と、サーバーの`quotation_api.rs`、`order_api.rs`、`order_inventory_transaction.rs`、`sales_contract_api.rs`、見積・受注ドメインの状態/金額検証を照合した。

この検証はiOS実機上でのファイル選択や、本番APIとのエンドツーエンド試験を代替しない。
