# 請求書のネイティブ業務フロー

比較した契約はWebの `invoices/invoice-api.ts`、`invoice-email-api.ts`、`invoice-detail-page.tsx` と、APIの `invoice_api/crud/update.rs`、`void_invoice.rs`、`invoice_email_api.rs`。比較基準のコミットは全体の[対応表](native-management-parity.md)を参照。

## 対応する操作

請求書画面では、登録済み取引先または未登録の宛名を指定し、整数数量の明細と税額を入力して下書きを作成できる。単価と税額は通貨の最小単位に正確に変換し、合計の桁あふれを検証する。下書き作成そのものでは通知を送信しない。

保存後は次の操作を行える。各送付・状態変更・取消には、対象と金額を表示したうえで確認欄への入力を要求する。

| 画面 | 操作 |
| --- | --- |
| 請求書 | 連絡先と備考の編集、下書き・送付済み・送付失敗・期限超過への状態変更 |
| 請求書 | 状態変更に伴うStripe支払リンクの作成と請求案内メール送信、支払案内の再送 |
| 請求書 | 保留・失敗中の支払リンク作成、メール・SMS送信の再処理 |
| 請求書 | 接続済みGmailから請求書PDFを添付して送付。宛先・件名・本文・PDF上の担当者を入力 |
| 請求書のメール送付履歴 | 請求書を選択し、APIが返す最新100件の宛先・件名・添付名・送付日時・失敗理由を閲覧 |
| 請求書の取消確認 | 請求書を選択し、取消可否・不可理由・逆仕訳予定日・対象仕訳数・会計期間を閲覧。理由と確認を入力して取消・逆仕訳を実行 |

GmailでのPDF送付は、請求の元になった下書き販売契約を有効化する場合がある。その業務上の副作用を確認画面の説明に表示する。接続設定そのものは今回の画面には含めない。

## 状態と再送の制御

入金済みへの手動変更はサーバーが禁止しているため、選択肢に含めない。支払済み・取消済みの請求書には、状態変更や請求案内の再送を提示しない。取消済みでは連絡先編集やPDFメール送付も提示しない。

送付前に請求書を取得し直し、更新日時、状態、宛名、送付先、明細、金額、期限、通知の状態が確認時と一致することを検証する。通常の状態変更APIには原子的な期待版条件がないため、この事前確認と書込の間の競合を完全に排除するものではない。最終的な認可と業務状態の制約はAPIでも検証される。

メール・SMS・支払リンクは、HTTP応答が成功でも、要求した処理が失敗・保留・未確認なら完了扱いにしない。請求書の更新が保存されていることを明記して、最新状態・履歴の確認を案内する。

Gmail送付の `requestKey` は同じ送付試行で保持する。再試行では履歴から同じキーの結果を回収し、送付後に請求書の更新日時が変わっていても二重送信を避ける。失敗済みの試行を新しくやり直す場合は、履歴を確認して画面を開き直す。通常の状態変更・再送・再処理にはAPIの冪等性保証がないため、不明な結果のまま同じ画面から連打して再送できない。

取消は、確認時と実行前の取消可否・逆仕訳計画を照合する。送信には同じ `Idempotency-Key` と取消理由を使う。取消自体が記録済みで逆仕訳が未完了の場合は、サーバーの再処理契約に従って同じキーで再試行できる。理由の上限はAPIと同じ1,024文字。

## 残る差分

PDFの端末への保存・印刷、Stripe/Gmailの新規接続、明細の小数数量、入金消込や返金はこの追加の対象に含まない。実機と実テナントを使う結合確認は未実施。金額変換、未登録請求先、権限・状態条件、送付失敗、更新競合、取消キー、URLのエスケープをローカルのテストで検証する。
